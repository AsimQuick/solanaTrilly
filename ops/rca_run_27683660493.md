The failure occurred during `docker compose pull`, specifically while Docker's
containerd daemon was extracting the largest layer of the web image
(`b338df4614ce`, 195.1 MB, the Python 3.12 site-packages layer). The VPS had
sufficient network connectivity to download the layer but could not write the
extracted bytes to the overlayfs snapshot directory.

## Root Cause

**VPS disk space exhaustion in `/var/lib/containerd` overlayfs storage.**

The VPS ran out of available disk space on the partition hosting the Docker /
containerd snapshot store. When `docker compose pull` fetched the new
`ghcr.io/asimquick/solanatrilly:latest` image, the containerd daemon attempted
to extract layer `b338df4614ce` (195.1 MB) to a new overlayfs snapshot at
`/var/lib/containerd/io.containerd.snapshotter.v1.overlayfs/snapshots/4475/`.
The write failed mid-extraction with the OS-level ENOSPC error ("no space left
on device"), killing the pull and the entire deploy step.

The disk was exhausted by accumulated Docker image layers from prior sprint-10
deploy runs. Each deploy pulls a new image (tagged `:latest` + `:<sha>`), and
the old layers are not automatically pruned — they accumulate in
`/var/lib/containerd/` until the partition fills. By the US-47 deploy
(2026-06-17T10:53Z, the 7th or 8th deploy run in the sprint), the VPS had
no remaining space for a 195 MB extraction.

**This is a deploy-context / VPS infrastructure condition, not a code regression.**

## Verification Against the Run Logs

The root cause is verified by the literal error in job 81877608439:

1. **Layer being extracted:** `b338df4614ce` — the 195.1 MB Python 3.12
   site-packages layer of `ghcr.io/asimquick/solanatrilly:latest`
2. **Write target:** `/var/lib/containerd/io.containerd.snapshotter.v1.overlayfs/snapshots/4475/fs/usr/local/lib/python3.12/site-packages/django/contrib/admin/locale/ko/LC_MESSAGES/djangojs.po`
3. **OS error:** `no space left on device` (POSIX ENOSPC) — this is
   unambiguous: the VPS partition hosting `/var/lib/containerd` had zero
   free bytes at the moment of the write
4. **Timing:** failure at T+7s into the pull step, exactly when the largest
   layer finishes downloading and extraction begins — consistent with disk
   exhaustion during write, not download

The US-40 unified workflow_call gate was GREEN (ci.yml `test` job passed on
the same commit), confirming this is a deploy-context infrastructure failure
and not a test/lint/code failure.

## Resolution (prerequisite for AC-53.2)

Add a `docker image prune -f` step on the VPS **before** `docker compose pull`
to reclaim disk from unused / dangling image layers accumulated from prior
deploy runs. This ensures the VPS has sufficient free space for each new image
pull regardless of deploy history.

```diff
  ssh ... "${VPS_USER}@${VPS_HOST}" \
-   'docker compose -p solanatrilly -f /root/solanatrilly/docker-compose.staging.yml down --remove-orphans; \
-    docker compose -p solanatrilly -f /root/solanatrilly/docker-compose.staging.yml pull && \
-    docker compose -p solanatrilly -f /root/solanatrilly/docker-compose.staging.yml up -d --remove-orphans'
+   'docker image prune -f; \
+    docker compose -p solanatrilly -f /root/solanatrilly/docker-compose.staging.yml down --remove-orphans; \
+    docker compose -p solanatrilly -f /root/solanatrilly/docker-compose.staging.yml pull && \
+    docker compose -p solanatrilly -f /root/solanatrilly/docker-compose.staging.yml up -d --remove-orphans'
```

The `docker image prune -f` removes all dangling images (layers not referenced
by any tag) without requiring interactive confirmation and without the
`--all` flag (so tagged images like the current `:latest` are preserved).
This is safe and scoped: it only removes unreferenced layers, not running
containers or named volumes. The `-p solanatrilly` isolation is maintained
because `docker image prune` operates on the image store, not on the compose
project namespace.
